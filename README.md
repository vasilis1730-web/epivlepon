# Σύστημα Ελέγχου Επίβλεψης Δημοσίων Έργων — Μοντέλο Δεδομένων & Σχήμα Βάσης

Πλήρες σχήμα PostgreSQL/Supabase για τον «Απόλυτο Οδηγό & Σύστημα Ελέγχου Επίβλεψης
Έργων», από την υπογραφή της σύμβασης έως τη Βεβαίωση Περάτωσης και την παραλαβή.

**Νομικό πλαίσιο:** ν. 4412/2016, Βιβλίο Ι, Μέρος Β΄ (άρθρα 134-175), όπως ισχύει
μετά τον ν. 4782/2021 (Α΄36). Επαληθεύτηκε ότι οι ν. 5218/2025 και ν. 5313/2026 δεν
μετέβαλαν τις διατάξεις εκτέλεσης έργων (ο ν. 5313/2026 τροποποίησε μόνο την παρ. 8
του άρθρου 54).

## Εγκατάσταση

### Supabase

```bash
supabase db push          # με τα migrations στον φάκελο supabase/migrations
```

ή, από το SQL Editor του Supabase, εκτέλεση των αρχείων με τη σειρά αρίθμησης.

Η σύνδεση των προφίλ με το `auth.users`, τα δικαιώματα, οι κάδοι αποθήκευσης και τα
πρότυπα εγγράφων εγκαθίστανται αυτόματα από τα migrations 0015–0019.

Στη συνέχεια αναπτύσσεται η συνάρτηση παραγωγής εγγράφων:

```bash
supabase functions deploy generate-document
```

### Front-end

```bash
cd app
cp .env.example .env.local     # συμπληρώστε VITE_SUPABASE_URL / VITE_SUPABASE_ANON_KEY
npm install && npm run dev
```

Χωρίς μεταβλητές περιβάλλοντος η εφαρμογή εκκινεί σε **λειτουργία επίδειξης** με
ενσωματωμένα δεδομένα — και παράγει κανονικά έγγραφα, τοπικά.

### Τοπικό PostgreSQL (δοκιμή)

```bash
createdb epivlepsi
psql -d epivlepsi -f tests/supabase_stubs.sql   # υποκατάστατα auth/storage
psql -d epivlepsi -f schema_full.sql
psql -d epivlepsi -f tests/test_failsafe.sql
```

## Πώς λειτουργεί το fail-safe

Κάθε έργο παίρνει αντίγραφο της πρότυπης ροής με μία κλήση:

```sql
select app.instantiate_workflow('<project_id>');
```

Το στάδιο δεν κλείνει αν εκκρεμούν:

1. **προαπαιτούμενα στάδια** (`stage_prerequisites`),
2. **υποχρεωτικές ενέργειες** της λίστας ελέγχου (`stage_tasks`),
3. **υποχρεωτικά έγγραφα** (`stage_documents`),
4. ο **ειδικός νομικός κανόνας** του σταδίου (`workflow_stages.guard_fn`).

Η προσπάθεια παραβίασης επιστρέφει σφάλμα με πλήρη αιτιολογία και παραπομπές:

```
ΑΠΑΓΟΡΕΥΕΤΑΙ η μετάβαση του σταδίου σε «completed».
Εκκρεμούν:
• Εκκρεμεί το προαπαιτούμενο στάδιο «Υποβολή & έγκριση χρονοδιαγράμματος κατασκευής». [N4412/145/1]
• Εκκρεμεί το προαπαιτούμενο στάδιο «ΣΑΥ / ΦΑΥ & μέτρα ασφάλειας». [PD305/1996]
• Εκκρεμής υποχρεωτική ενέργεια (Διευθύνουσα Υπηρεσία): Παράδοση χώρου εκτέλεσης εργασιών [N4412/137]
• Λείπει το υποχρεωτικό έγγραφο: Πρωτόκολλο παράδοσης χώρου εργασιών. [N4412/137]
```

**Παράκαμψη:** μόνο ο Προϊστάμενος της Δ.Υ. ή η Προϊσταμένη Αρχή, με υποχρεωτική
αιτιολόγηση (`override_reason`), και η ενέργεια καταγράφεται ανεξίτηλα στο `audit_log`.

## Διαχωρισμός ρόλων

Ο πίνακας `app.table_access` αποτυπώνει, ανά πίνακα, ποιος διαβάζει και ποιος γράφει.
Οι πολιτικές RLS παράγονται αυτόματα από αυτόν.

| Ρόλος | Δικαιώματα |
|---|---|
| **Επιβλέπων** | Πλήρης ανάγνωση των έργων του· συντάσσει εκθέσεις, ΠΠΑΕ, ελέγχους, εισηγήσεις |
| **Προϊστάμενος Δ.Υ.** | Όλα τα έργα του φορέα· εγκρίσεις, ρήτρες, εγγυήσεις, παράκαμψη κλειδώματος |
| **Προϊσταμένη Αρχή** | Εγκρίσεις ΑΠΕ, παρατάσεων, επιτροπών, αποφάσεις επί ενστάσεων |
| **Ανάδοχος** | «Θυρίδα υποβολής»: ημερολόγιο, επιμετρήσεις, αφανείς, λογαριασμοί, αιτήματα. Βλέπει μόνο ό,τι του έχει κοινοποιηθεί. **Δεν τροποποιεί ό,τι έχει ήδη υποβάλει** |
| **Επιτροπές** | Μόνο τα έργα και τα πρωτόκολλά τους |

## Αυτοματοποίηση εγγράφων

```
document_templates  →  πρότυπα .docx της Υπηρεσίας (Supabase Storage) ή ενσωματωμένο HTML
template_fields     →  χάρτης «placeholder → πηγή δεδομένων» (δηλωτικός, χωρίς κώδικα)
documents           →  τα παραχθέντα έγγραφα, με πρωτόκολλο, ΑΔΑ/ΑΔΑΜ, checksum, payload
```

Η προσθήκη νέου προτύπου γίνεται από τη διοίκηση, χωρίς αλλαγή κώδικα: ανεβάζετε το
αρχείο, δηλώνετε τα πεδία του και το αντιστοιχίζετε σε στάδιο (`stage_code`).

### Edge Function `generate-document`

```
POST /functions/v1/generate-document
{ "project_id": "…", "doc_code": "BEBAIOSI_PERATOSIS", "entity_id": null, "dry_run": true }
```

Ροή εκτέλεσης:

1. Ο πελάτης Supabase δημιουργείται **με το JWT του καλούντος** — ισχύουν όλα τα RLS
   policies. Δεν χρησιμοποιείται service-role κλειδί.
2. `context.ts` συνθέτει το αντικείμενο δεδομένων του εγγράφου. Τα πρότυπα δηλώνουν
   **διαδρομές** μέσα σε αυτό (`contracts.signed_at`), ποτέ SQL.
3. `render.ts` αντικαθιστά τα `{{…}}`. Μια σειρά πίνακα με `{{#each grammes}}`
   επαναλαμβάνεται για κάθε γραμμή επιμέτρησης. Στα .docx ενοποιούνται τα σπασμένα
   `<w:t>` ανά παράγραφο πριν την αντικατάσταση.
4. Απόδοση αριθμού πρωτοκόλλου (`next_protocol_no`), αποθήκευση στον κάδο `documents`,
   καταχώριση στον πίνακα `documents` με SHA-256 checksum, επιστροφή υπογεγραμμένου
   συνδέσμου μίας ώρας.

Με `dry_run: true` επιστρέφεται μόνο προεπισκόπηση: χωρίς πρωτόκολλο, χωρίς αποθήκευση.
Η απάντηση περιλαμβάνει πάντα `missing_fields` — τα υποχρεωτικά πεδία που έμειναν κενά.

**Έτοιμα πρότυπα:** `APOFASI_ORISMOU` (άρθρο 136 §2), `EGKRISI_XRONOD` (145 §2),
`PPAE` (151 §7), `ANAL_EPIMETRISI` (151 §2), `BEBAIOSI_PERATOSIS` (168 §2),
`PRAXH_MEIWSHS_EGG` (72 §14β).

## Νυχτερινή αυτοματοποίηση προθεσμιών

`app.run_nightly_jobs()` — εκτελείται κάθε βράδυ στις 02:15 UTC μέσω `pg_cron`
(εργασία `epivlepsi-nightly`) και αποτυπώνει στη βάση ό,τι **έχει ήδη επέλθει από
τον νόμο**:

| Ενέργεια | Διάταξη |
|---|---|
| Τεκμήριο έγκρισης χρονοδιαγράμματος | άρθρο 145 §2 |
| Εγκριτική πράξη αφανών εργασιών (30 ημέρες) | άρθρο 151 §7 |
| Σιωπηρή έγκριση λογαριασμού | άρθρο 152 |
| Σιωπηρή αποδοχή παράτασης | άρθρο 147 §5 |
| Σήμανση υπερημερίας επιβλέποντος (3ήμερο αφανών) | άρθρο 151 §7 |
| Σήμανση εκπρόθεσμων σταδίων | — |
| Υπολογισμός ειδικής ποινικής ρήτρας ημερολογίου | άρθρο 146 |

Δύο σχεδιαστικές επιλογές που αξίζει να σημειωθούν:

**Η εργασία δεν επιβάλλει κυρώσεις.** Η ρήτρα ημερολογίου καταχωρίζεται ως
*υπολογισμός*, χωρίς αριθμό και ημερομηνία απόφασης· η επιβολή παραμένει πράξη της
Διευθύνουσας Υπηρεσίας. Η αιτιολογία κάθε εγγραφής το δηλώνει ρητά.

**Οι τμηματικές επιμετρήσεις δεν εγκρίνονται σιωπηρά.** Ο νόμος προβλέπει τεκμήριο
έγκρισης για το χρονοδιάγραμμα, τις αφανείς εργασίες, τους λογαριασμούς και τις
παρατάσεις — όχι για τις επιμετρήσεις. Αυτές απλώς σημαίνονται ως εκπρόθεσμες.

Κάθε εκτέλεση καταγράφεται στο `app.nightly_runs` με το πλήρες αποτέλεσμα, ώστε να
είναι ελέγξιμο τι μεταβλήθηκε και πότε.

## Δοκιμές

### Κανόνες fail-safe

`tests/test_failsafe.sql` — 12 σενάρια, όλα επιτυχή σε PostgreSQL 16:

1. Δημιουργία ροής 35 σταδίων· το στάδιο Ι.Φ.Ε. εξαιρείται σε υπηρεσιακή επίβλεψη
2. Απαγόρευση κλεισίματος σταδίου με εκκρεμότητες (με πλήρη αιτιολογία)
3. Ανάλυση εμποδίων σταδίου
4. Μείωση εγγύησης 70% — απόρριψη χωρίς τελική επιμέτρηση, επιτυχία μετά
5. Όρια ΑΠΕ: 50%, 20% ανά ομάδα, 10% συνολικά, γνωμοδότηση Τ.Σ.
6. Αφανείς: 3ήμερη προθεσμία και υποχρεωτική φωτογραφική τεκμηρίωση
7. Δειγματοληψία: 6 επιμετρήσεις → 4 έλεγχοι, 20 → 8
8. Αυτόματος υπολογισμός προθεσμιών
9. Έλεγχος λογαριασμού χωρίς εγκεκριμένη επιμέτρηση
10. Βεβαίωση Περάτωσης → αυτόματο άνοιγμα συντήρησης, παραλαβής, επιτροπής
11. Πίνακας ελέγχου & οικονομική εικόνα
12. Audit trail

### Έναρξη επίβλεψης νέου έργου

`tests/test_create_project.sql` — 8 έλεγχοι της `public.create_project_full()`:

1. Ο επιβλέπων **δεν** ανοίγει έργο (άρθρο 136 §2)
2. Ο Προϊστάμενος Δ.Υ. το ανοίγει και δημιουργούνται τα στάδια
3. Απόρριψη διπλού κωδικού, απροβλέπτων εκτός 9%/15%, μηδενικής προθεσμίας, έργου χωρίς επιβλέποντα
4. Οικονομικά μεγέθη — τα ίδια με τον υπολογισμό του front-end, στο λεπτό
5. Προθεσμίες κατά τα άρθρα 147 §2 και §4
6. Απολογισμός δημιουργίας (στάδια, ενέργειες, ορισμοί, εγγυήσεις)
7. Ο ορισθείς επιβλέπων βλέπει πλέον το έργο του μέσω RLS
8. Κατάλογος προσωπικού του φορέα για τις λίστες επιλογής

### Απόδοση προτύπων εγγράφων

```bash
node tests/fnharness/harness.mjs
```

Τρέχει τον **πραγματικό** κώδικα της Edge Function (`context.ts` / `render.ts` /
`format.ts`) πάνω σε στιγμιότυπα της βάσης, με ψεύτικο πελάτη Supabase, και ελέγχει
για κάθε πρότυπο: αναντικατάστατα `{{…}}`, κενά υποχρεωτικά πεδία, `undefined`,
`[object Object]`, `NaN`. Δύο σενάρια — έργο σε εκτέλεση και έργο σε περαίωση.

## Αφετηρία των προθεσμιών

Κάθε στάδιο δηλώνει **από ποιο γεγονός** αρχίζει να τρέχει η προθεσμία του
(`workflow_stages.deadline_basis`). Η `app.compute_stage_due()` υπολογίζει
ημερομηνία **μόνο όταν το γεγονός αυτό έχει επέλθει**:

| Αφετηρία | Πηγή | Διάταξη |
|---|---|---|
| `ypografi_symvasis` | `contracts.signed_at` | 147 §2 |
| `enarxi_ergasion` | `contracts.works_start_deadline` | 145 §2 |
| `lixi_prothesmias` | `contracts.current_end_date` | 147 §1 |
| `bebaiosi_peratosis` | `completions.certificate_issued_at` | 168 §2 |
| `lixi_syntirisis` | `maintenance_periods.ends_on` | 171 |
| `ypovoli_eggrafou`, `koinopoiisi_praxis`, `custom` | — (ανά εγγραφή) | — |

Οι τρεις τελευταίες αφετηρίες αφορούν γεγονότα που επαναλαμβάνονται ανά έγγραφο ή
ανά πράξη — υποβολή επιμέτρησης, κοινοποίηση δήλωσης αφανών, αίτημα παράτασης. Οι
προθεσμίες τους τηρούνται στην ίδια την εγγραφή (`approval_due`, `inspection_due`,
`decision_due`) και **όχι** στο στάδιο, το οποίο μένει χωρίς ημερομηνία.

**Γιατί έχει σημασία:** παλαιότερα κάθε άγνωστη αφετηρία έπεφτε σιωπηλά στην
ημερομηνία υπογραφής. Έτσι η «Έκδοση Βεβαίωσης Περάτωσης» εμφανιζόταν *εκπρόθεσμη
κατά 145 ημέρες* σε έργο που μόλις είχε ξεκινήσει. Ένας επιβλέπων που βλέπει ψευδείς
συναγερμούς μαθαίνει να αγνοεί τις ειδοποιήσεις — και τότε το σύστημα ελέγχου
χειροτερεύει την κατάσταση αντί να τη βελτιώνει. Καμία προθεσμία δεν επινοείται.

Μόλις εμφανιστεί μια αφετηρία (εκδοθεί η Βεβαίωση Περάτωσης, οριστεί η περίοδος
συντήρησης, μεταβληθεί η προθεσμία της σύμβασης), triggers στους πίνακες
`completions`, `maintenance_periods` και `contracts` καλούν την
`app.recompute_stage_dues()` και οι ημερομηνίες συμπληρώνονται αυτόματα.
